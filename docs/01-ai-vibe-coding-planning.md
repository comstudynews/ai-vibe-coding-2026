# 제1장. 생성형 AI·바이브 코딩과 소프트웨어 기획
## 1.1 학습목표
① 생성형 AI가 개발에서 맡는 역할과 한계를 설명합니다.
② 바이브 코딩과 책임 있는 AI 보조 개발을 구분합니다.
③ 위젯·컴포넌트·레이아웃을 실제 React 화면에서 식별합니다.
④ PoC·Prototype·MVP·Pilot이 각각 무엇을 검증하는지 설명합니다.
## 1.2 생성형 AI와 바이브 코딩
### 1.2.1 생성형 AI와 코드 생성
생성형 AI는 입력한 지시와 문맥을 바탕으로 텍스트·코드 등 새로운 결과물을 생성하는 AI입니다. 소프트웨어 개발에서는 요구사항 분해, 코드 생성, 테스트 초안, 오류 분석, 문서화 등 여러 작업을 보조합니다. 그러나 결과가 올바르다는 보증은 없으며, 개발자는 변경 내용을 검증해야 합니다.
### 1.2.2 바이브 코딩
바이브 코딩은 자연어로 원하는 동작을 설명하고 AI가 제안한 코드를 중심으로 빠르게 애플리케이션을 만드는 개발 접근입니다. 프로토타입이나 아이디어 탐색에는 유용하지만, 생성한 코드를 이해·검증하지 않고 서비스를 공개하는 것은 위험합니다.
**강의 핵심 문장:** AI는 코드를 작성할 수 있지만, 요구사항의 타당성·데이터 보호·결과 검증·서비스 운영에 대한 책임은 개발자에게 있습니다.
## 1.3 UI 설계: 위젯, 컴포넌트, 레이아웃
### 1.3.1 용어

| 용어 | 의미 | 중고차 앱 사례 |
| --- | --- | --- |
| 위젯·UI 요소 | 사용자가 조작하거나 정보를 읽는 개별 인터페이스 요소 | 검색 입력창, 등록 버튼, 가격 표시 |
| React 컴포넌트 | 상태·속성·UI 구조를 갖춘 재사용 가능한 화면 단위 | CarForm, CarList, CarCard |
| 레이아웃 | 컴포넌트를 화면 크기에 맞추어 배치하는 구조 | 검색 영역, 목록 그리드, 등록 양식 |
| 반응형 디자인 | 화면 너비에 따라 배치를 조정하는 설계 | 데스크톱 2열 → 모바일 1열 |

Flutter의 Widget과 React의 Component는 프레임워크별 중심 추상화가 다릅니다. 이번 예제에서는 React 기준으로 **컴포넌트**를 사용하고, '위젯'은 일반적인 화면 요소를 가리키는 말로 설명합니다.
### 1.3.2 중고차 앱 와이어프레임
```plain text
┌───────────────────────────────────┐
│ 중고차 매물 관리        [매물 등록]│
├───────────────────────────────────┤
│ 전체 3대    |   검색: [________] │
├───────────────────────────────────┤
│ [현대 쏘나타] 2022 / 38,000km     │
│ 1,850만원           [수정][삭제] │
├───────────────────────────────────┤
│ [기아 K7]     2020 / 72,000km     │
│ 1,690만원           [수정][삭제] │
├───────────────────────────────────┤
│ 새 매물 등록 폼                    │
│ 차량명 / 연식 / 주행거리 / 가격    │

```
이 화면에서는 색채와 장식을 먼저 고르는 대신 **입력 → 목록 반영 → 수정 → 삭제**라는 핵심 사용자 흐름을 우선 검증합니다.
## 1.4 PoC·Prototype·MVP·Pilot 구분

| 개념 | 핵심 질문 | 예제 적용 |
| --- | --- | --- |
| PoC (Proof of Concept) | 기술적으로 가능한가? | Codex가 기존 React·Express 프로젝트를 분석·수정하고 API 통신을 구현하는가? |
| Prototype | 만들려는 화면·상호작용이 예상대로 동작하는가? | 매물 목록·등록·수정·삭제를 화면에서 확인 |
| MVP (Minimum Viable Product) | 최소한의 제품으로 실제 사용자 가치·가설을 검증할 수 있는가? | 실사용자가 CRUD를 사용하며 데이터가 보존되고 피드백을 제공 |
| Pilot | 제한된 실제 운영 환경에서 서비스가 적합한가? | 특정 판매점·학과 등 소수 사용자에게 기간을 정해 시범 운영 |

**유의:** 네 항목이 항상 PoC → Prototype → MVP → Pilot 순서로 일어나는 것은 아닙니다. MVP는 제품 범위·가치 검증의 개념이고, Pilot은 운영 환경에서의 검증 방식입니다. MVP를 이용해 Pilot을 할 수도 있습니다.
### 1.4.1 오늘 만드는 결과물의 정확한 이름
이번 시연 결과는 **메모리 기반 중고차 관리 CRUD 프로토타입**입니다. Express 서버가 재시작되면 저장 데이터가 초기화되므로 지속 사용 가능한 MVP라고 부르지 않습니다. **이번 중고차 매물 관리 앱**을 지속적으로 이용하는 MVP로 확장하려면 영구 저장, 적절한 접근 통제, 입력 검증, 사용자 피드백 수집 등이 필요합니다. 다만 데이터베이스나 로그인은 모든 MVP의 보편적인 필수 조건이 아닙니다. MVP는 최소 구성으로 사용자 가치와 가설을 검증하는 접근입니다.
### 1.4.2 요구사항과 검증 기준
**사용자 스토리:** 관리자는 차량명·연식·주행거리·가격을 등록하고 목록에서 조회·수정·삭제하고 싶습니다. 이를 통해 반복되는 매물 관리 업무를 간소화합니다.
**인수 기준:**
① 등록한 매물이 화면에 나타납니다.
② 빈 차량명·음수 가격·잘못된 연식은 거부됩니다.
③ 수정 후 목록에 변경된 값이 반영됩니다.
④ 삭제 후 해당 매물이 목록에서 사라집니다.
⑤ 비공개 개발 환경에서는 CRUD가 작동하고, 서버 재시작 시 메모리 데이터가 초기화된다는 점을 이해합니다.
⑥ 공개 클라우드 배포에서는 조회만 허용하고 쓰기 요청은 403으로 차단하는 이유를 설명합니다.
## 1.5 정리
- 생성형 AI의 생산성 향상과 코드 품질 보증은 다른 문제입니다.
- UI 구성 용어를 React 컴포넌트에 연결해야 구현 설명이 선명해집니다.
- PoC, Prototype, MVP, Pilot은 **무엇을 검증하는가**에 따라 구분합니다.
**강의자 메모:** 실습 전에 완성될 매물 관리 앱의 화면을 약 30초 보여 주고, 모든 이론을 이 화면에 다시 연결합니다.
